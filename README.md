# Антифрод ДЗ 3

CPU-сервис читает транзакции из Kafka, возвращает `score`, `fraud_flag`, `transaction_id`, `model_version` и сохраняет результаты в PostgreSQL. Airflow поставляет новые размеченные месяцы, переобучает CatBoost и проверяет качество данных. 

## Запуск

1. Склонируйте этот репозиторий и перейдите в его каталог. Скачайте train.csv с колонкой target
2.  Создайте настройки:

```bash
cp .env.example .env
```

В `.env` замените `TRAIN_DATA_CSV` на **абсолютный путь** к файлу. 

3. Выполните:

```bash
docker compose config --quiet
docker compose up -d --build
docker compose ps -a
```

Airflow: http://localhost:8081, логин и пароль: admin / admin.

## Архитектура и DAG

Все сервисы находятся в одной сети. model_registry смонтирован в Airflow как /opt/airflow/models, в скоринг как /models. training_data хранит parquet-снимки. Каталог reports/ на хосте смонтирован в /opt/airflow/reports, рядом с каталогом моделей внутри Airflow.

В dags/ только сборка графов; функции и docstring находятся в pipeline/. Все три DAG запускаются каждые 5 минут, catchup=False, max_active_runs=1; доступны ручные запуски. По одной повторной попытке через 30 секунд. SequentialExecutor ограничивает параллельную нагрузку в учебном окружении.

### supply_labeled_batch

`sample_next_month → append_labeled_batch → prune_old_months`

Выбирает до **100 000** уже существующих строк и переносит их в месяц после максимального `transaction_time`. Сохраняет день, час и минуту; например, 31 января при переносе в февраль становится 28/29 февраля. Удаляет наблюдения раньше первого числа самого нового месяца минус **3 года**. Граница включается в хранимые данные.

Месяц закрепляется за Airflow `run_id` в `pipeline_runs` до создания файла. Снимок батча сохраняется атомарно. `COPY` и запись в `supplied_months` фиксируются одной транзакцией: повтор после успешного commit не вставляет строки снова. Следующий прогон возобновляет незавершённый зарезервированный месяц. Блокировка PostgreSQL согласует поставку, очистку и публикацию.

Если поставка опережает обучение настолько, что очистка затронет нужное окно, поставка временно становится `skipped`. После продвижения обучения она продолжится; необходимая история не удаляется.

### `retrain_catboost`

`extract_month_batch → slide_training_window → time_train_test_split → preprocess_dataset → fit_catboost → evaluate_model → publish_model`

Окно имеет фиксированные **3 календарных месяца**: первые два идут в train, последний - в test. Исходное окно январь–март 2019; первый обрабатываемый месяц - апрель 2019. Поставка новых месяцев стартует после конца CSV: для исходного датасета это апрель 2020. Переобучение постепенно доходит и до этих данных.

Границы окна вычисляются от зарезервированного месяца и выбираются из витрины. Окно не строится повторным добавлением строк к изменяемому файлу. Поэтому сбой между сохранением файлов и commit БД не дублирует месяц и не удаляет второй старый месяц. Требуются ровно три месяца и оба класса в train и test. Если следующий месяц ещё не поставлен, извлечение становится `skipped`.

Артефакты разделены по месяцу; `training_state` изменяется только после сохранения бинарника кандидата и решения проверки качества. Обновление состояния условное и под блокировкой. Очистка и повтор того же Airflow-прогона используют прежний месяц, а повтор завершённой публикации не откатывает рабочую модель и не продвигает указатель второй раз.

### Собственный препроцессинг

Обучение и скоринг вызывают одну функцию `fraud_detector/src/preprocessing.py:run_preproc`. Помимо совместимых с исходной моделью календарных признаков и расстояния Haversine добавлены:

- логарифмы суммы, населения города и расстояния;
- циклические sin/cos часа с учётом минут и дня недели;
- признак ночной операции;
- отношение суммы к `1 + расстояние.`

Категории имеют одинаковый строковый тип; пустые категории заменяются на `__missing__`. Имена и адрес удаляются. Признаки вычисляются только из текущей транзакции, без агрегатов по target или будущим строкам. Исходный DataFrame не меняется. Старые признаки сохранены, поэтому стартовая и новые модели работают с тем же входным контрактом.

### Допуск модели в prod

В комплекте воспроизводимая стартовая модель, обученная только на январе–феврале 2019 (76 593 строки), с теми же CPU-параметрами и собственными признаками. Март и последующие контрольные месяцы в её обучение не включены. Она копируется в общий каталог с версией `initial` только при первом запуске; существующая prod-модель не заменяется. Рецепт: `pipeline/retrain/bootstrap.py`. При необходимости воспроизвести бинарник на загруженном исходном датасете:

```bash
docker compose exec -T airflow python -m pipeline.retrain.bootstrap
docker compose cp airflow:/tmp/bootstrap.cbm fraud_detector/models/my_catboost.cbm
```

Эти команды меняют только стартовый артефакт для будущих образов, не `latest.txt` работающего сервиса.

CatBoost обучается на CPU, 100 фиксированных итераций, `random_seed=42`, 4 потока. Test не участвует в обучении или ранней остановке.

Кандидат и текущая prod-модель оцениваются **на одних и тех же строках самого свежего месяца**. Рассчитываются:

- PR-AUC через `average_precision_score`, полезная при редком фроде;
- ROC-AUC;
- F1 при пороге `score > 0.5`.

Публикация разрешена, только если **все три метрики конечны и ни одна не ниже метрики действующей модели** (допуск округления `1e-12`). Сравнивать с сохранёнными метриками другого месяца было бы некорректно. При отсутствии пригодного test или рабочей модели задача завершается ошибкой, обхода проверки нет.

Сначала сохраняются `/opt/airflow/models/candidates/cpu_v2_YYYYMM.cbm`, `.training.json` и `.decision.json`. Решение содержит метрики обеих моделей, исходную версию, месяц и `accepted`. При одобрении создаются `my_catboost_cpu_v2_YYYYMM.cbm`, `.metrics.json` и атомарно заменяется `latest.txt`. Скоринг читает этот указатель перед каждым сообщением и загружает новую версию без перезапуска.

**Отклонение - успешный обработанный месяц:** кандидат и решение остаются в архиве, prod не меняется, окно и указатель продвигаются после сохранения этих артефактов. Иначе один неудачный месяц навсегда остановил бы скользящее обучение. Таким образом, новый бинарник после обучения появляется всегда, а новая рабочая версия — только после прохождения допуска. Качество не подделывается ради демонстрации смены версии.

## Data Quality

`data_quality`: `collect_quality_stats → write_quality_report → enforce_quality`.

Семь проверок выполняются по согласованному снимку PostgreSQL в read-only транзакции.

| Правило | Требование |
| --- | --- |
| `schema` | Все 18 обязательных колонок загрузчика присутствуют и имеют ожидаемые SQL-типы |
| `nonempty` | Витрина непустая |
| `nonnull` | Ни в одной обязательной колонке нет NULL |
| `nonblank_categories` | Текстовые поля не пустые и не состоят из пробелов |
| `binary_target` | Метка принадлежит `{0, 1}` |
| `positive_finite_amount` | Сумма конечна и строго положительна |
| `coordinates` | Обе широты в `[-90,90]`, обе долготы в `[-180,180]` |

Для каждого прогона сохраняются `reports/dq_<hash_run_id>.html` и `.json`, последний HTML доступен как `reports/latest.html`. Отчёт содержит время, размер и период снимка, правила и число нарушений. Затем `enforce_quality` помечает DAG ошибкой, если есть нарушения. Поэтому HTML доступен и после неуспешной проверки. Повторы заменяют отчёт того же прогона, а витрину не меняют. Это отдельная диагностическая проверка, не зависимость по расписанию между DAG.

## Ручной запуск и проверка результата

В Airflow запустите `supply_labeled_batch`, `retrain_catboost` и `data_quality` кнопкой Trigger DAG. Дождитесь зелёных задач.

Запустить их можно и через терминал:

```bash
docker compose exec -T airflow airflow dags trigger supply_labeled_batch
docker compose exec -T airflow airflow dags trigger retrain_catboost
docker compose exec -T airflow airflow dags trigger data_quality
```

Посмотрите файлы моделей и текущую версию:

```bash
docker compose exec -T airflow ls /opt/airflow/models /opt/airflow/models/candidates
docker compose exec -T airflow cat /opt/airflow/models/latest.txt
```

Проверьте последние результаты скоринга:

```bash
docker compose exec -T postgres psql -U fraud_user -d fraud_db -c 'SELECT score, fraud_flag, model_version FROM scores ORDER BY created_at DESC LIMIT 20;'
```

После публикации модели дождитесь новых транзакций. Их `model_version` должен совпадать с `latest.txt`. Сообщения также доступны в Kafka UI: `scoring` → Messages.

Если новая модель не принята (`accepted=false`), продолжает работать старая. Решение и метрики можно посмотреть командой:

```bash
docker compose exec -T airflow sh -c 'cat /opt/airflow/models/candidates/*.decision.json'
```

Результаты проверки данных находятся в reports

## Проверки реализации

После запуска контейнеров:

```bash
docker compose exec -T airflow python -m unittest discover -s /opt/airflow/tests -v
```

Девять тестов используют временные файлы и PostgreSQL TEMP-таблицы только в своей сессии, не изменяя рабочие данные. Проверяют согласованность признаков для батча и одной строки, отсутствие target leakage, перенос конца месяца, отклонение любой ухудшившейся/NaN-метрики, отсутствие дублей при повторной поставке, rollback ошибки COPY, восстановление после сохранения модели и ошибки БД, неизменность prod при отклонении, подхват новой модели тем же процессом скоринга и наличие HTML после неуспешного DQ.

## Структура

Остановить, сохранив данные: `docker compose stop`. Полностью начать заново: `docker compose down -v`, затем `docker compose up -d --build`. `down -v` **удаляет БД, модели, историю Airflow и parquet**, но HTML в `reports/` остаётся на хосте. Повторный обычный запуск существующую витрину не перезаливает.
